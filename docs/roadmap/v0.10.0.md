# v0.10.0 — Git-aware Primitives

> **Status:** Planned
> **Theme:** Make idx conscious of what the developer is actively working on

---

## Problem

The current index treats every file in the repository as equally reachable. An agent searching for a symbol retrieves results ranked by BM25 score and read popularity — but has no awareness of which files are part of the active change. When a developer is fixing a bug in `internal/auth/`, the agent gets the same result set it would return for a read-only audit of the codebase.

Two capabilities are missing:

1. **Scope search to recent changes.** There is no way to say "search only in the files that changed since this commit." Agents working on a diff-review or bug-triage task must either search the entire index (noisy) or manually filter results after the fact (expensive).

2. **Discover related files.** Given a file the agent is currently editing, there is no primitive to ask "what other files are most likely relevant to this?" Agents fall back to reading import graphs or running broad keyword searches, both of which miss the co-authorship signal that the read log has been collecting since v0.5.0.

---

## What we're building

### `--since <ref>` flag for `idx search`

Restricts the search corpus to files that have changed since a given Git ref.

```bash
# search only in files modified since the last commit
idx search "token validation" --since HEAD~1

# search in files changed on this branch relative to main
idx search "middleware" --since main --ext go
```

Internally, `--since` runs `git diff --name-only <ref>...HEAD`, collects the changed file set, and intersects it with the BM25 candidate list before ranking. Files not in the diff are excluded regardless of their BM25 score.

This is the same mechanism that powers the branch delta index in v1.0.0 — the git-diff-to-file-set computation is extracted as a shared primitive at this version.

**Supported ref formats:** commit SHA, branch name, tag, `HEAD~N`, and `@{upstream}`.

### `idx related <file>`

Returns the files most likely to be relevant given a file the agent is currently working on. Relevance is computed from two signals:

**Co-read affinity.** Files that appear together in the same read-log session window are likely worked on together. A high co-read count between `service.go` and `port.go` means an agent editing one will probably need the other.

**Term co-occurrence.** Files that share a significant vocabulary overlap in the BM25 index are likely in the same domain. This catches relationships not captured by the read log (e.g. a file that was never co-read but shares a dense set of domain terms).

The two signals are combined with a weighted sum, configurable via `.idx.yml`:

```yaml
related:
  co_read_weight: 0.7
  term_overlap_weight: 0.3
  limit: 10
```

```bash
# find files related to the one currently being edited
idx related internal/auth/middleware.go

# emit as JSON for agent consumption
idx related internal/auth/middleware.go --format json --compact
```

Output is a ranked list of file paths with a short explanation of the dominant signal (`co-read`, `term-overlap`, or `both`).

**Prerequisite:** `idx read` must be routed through idx (v0.9.0) for the co-read signal to carry meaning. An empty read log produces results based on term overlap only.

---

## User impact

| Before | After |
|---|---|
| Agents search the full index when reviewing a diff | `--since` scopes results to the changed file set |
| Agents discover related files through import graphs or broad searches | `idx related` surfaces co-read and term-overlap neighbors directly |
| Read log accumulates signal with no query interface | Co-read affinity becomes a first-class retrieval primitive |

---

## Success criteria

- `idx search "x" --since HEAD~3` returns only results from files in `git diff HEAD~3...HEAD`.
- `idx related <file>` returns a non-empty ranked list for any indexed file with co-read or term-overlap signal.
- `idx related` on a file with no read log entries falls back to term-overlap ranking without error.
- `--since` with an invalid ref returns a clear error that includes the offending value.
- Both features appear in `idx search --help` and `idx related --help` with usage examples.

---

## Dependencies

- **v0.9.0** — `idx read` must be part of the skill so agents populate the read log that `idx related` consumes.
